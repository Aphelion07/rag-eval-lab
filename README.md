# rag-eval-lab

**A retrieval evaluation harness. It answers which RAG configuration actually finds the right documents — with confidence intervals, failure analysis, and no API key.**

## Why this is not another RAG chatbot

Most RAG projects demonstrate that a pipeline *runs*. Almost none demonstrate that it **works** — that the retriever puts the right document in front of the model rather than a plausible neighbour.

That gap matters, because retrieval is the ceiling on everything downstream. A generator cannot cite what retrieval never returned, and no amount of prompt engineering repairs a document that was never fetched.

So this project has no chatbot in it. It has a corpus, a labelled question set, four chunking strategies, three retrieval strategies, and the machinery to say which combination wins and whether the win is real.

```bash
rag-eval run
```

## What it measures

| | |
|---|---|
| **Recall@k** | Did the relevant documents reach the top k at all? The ceiling on everything downstream. |
| **Precision@k** | How much of the top k is noise? Noise costs context window and dilutes attention. |
| **MRR** | How high did the *first* relevant document rank? |
| **nDCG@k** | Rank-weighted, and the only metric here that understands graded relevance — "answers it" versus "mentions it". |
| **hit rate** | Did the query get *anything* useful? The blunt question. |
| **Bootstrap CI** | A 95 % interval on every mean, so a two-point gap is not mistaken for a result. |
| **index / query time** | A configuration that wins on nDCG while querying 6× slower has not obviously won. |

Reporting Recall@k alone is the most common way to make a retriever look better than it is. All of them are computed for every run.

## The dataset

24 documents on IT security and networking, 40 questions, 66 graded relevance labels — written for this benchmark and generated by [`data/build_corpus.py`](data/build_corpus.py), so the design constraints stay visible and testable:

**Adjacent topics get separate documents.** Symmetric vs asymmetric encryption. Authentication vs authorization. TCP vs UDP. SQL vs command injection. A corpus of unrelated documents makes every retriever look good; the interesting failures only appear when the wrong answer is plausible.

**Vocabulary is deliberately split.** One document says *"Enable 2FA"*; the query asking for it says *"two-factor authentication"*. BM25 cannot bridge that gap — a test asserts it returns literally nothing. Other queries hunt exact strings (`port 22`, `A01`, `strcpy`) where the advantage reverses.

**Relevance is graded**, 2 for a document that answers the question and 1 for one that is merely related, so nDCG can distinguish a good ranking from a lucky one.

A test asserts that every document is reachable by some query. An unlabelled document is dead weight — it can only hurt precision, never help recall.

## Findings

All figures from `nomic-embed-text` via Ollama, k=5, 40 queries. Reproduce with `rag-eval run`.

### 1. The trivial chunker wins

`paragraph` — one chunk per paragraph, no size budget, no overlap logic — took the top three places. The recursive splitter that every RAG tutorial reaches for placed **fifth**, behind it on every metric.

Not a universal law: this corpus has short, well-structured documents where paragraphs are already the natural retrieval unit. That is exactly the point. The sophisticated strategy is not free, and on a corpus like this it buys nothing. A benchmark that omitted the trivial control would have concluded otherwise.

### 2. BM25 never whiffs — it just ranks badly

Look at the `hit` column across all twelve configurations:

| retriever | hit rate | nDCG |
|---|---|---|
| BM25 (all four chunkers) | **1.000** | 0.841 – 0.860 |
| dense | 0.775 – 0.975 | 0.839 – 0.892 |
| hybrid | 0.925 – 0.975 | 0.870 – 0.895 |

BM25 found something relevant for **every single query**, and still lost on ranking quality. Dense retrieval ranks better when it works and fails completely when it does not.

These are different risk profiles, not different amounts of quality. If a downstream generator can tolerate a mediocre ranking but not an empty context, the metric to optimise is hit rate, and the "worse" retriever is the correct choice.

### 3. Hybrid retrieval can be worse than its own best component

Query q04, *"How do I stop an attacker who guessed my credentials from getting in?"*:

```
$ rag-eval inspect --query q04
labelled relevant: ['authentication', 'two-factor-auth']

bm25                    dense                   hybrid (rrf)
  logging-monitoring      ssh                     logging-monitoring
  least-privilege      OK authentication          password-reset
  password-reset          csrf                    ssh
  buffer-overflow      OK two-factor-auth         least-privilege
OK authentication         password-reset          csrf
```

Both components retrieve something relevant. **The fusion of them retrieves nothing.**

Reciprocal Rank Fusion scores a document by summing `1/(k + rank)` across retrievers, so it rewards *agreement*. Here both retrievers independently rank `password-reset` moderately well — and their agreement on that wrong answer outweighs `authentication`, which only one of them ranks highly. Fusion amplified the shared error and diluted the unique signal.

Every tutorial says hybrid retrieval is better than either component. Usually it is. This is a reproducible case where it is not, and it is the reason the harness reports per-query failures rather than only aggregates.

### 4. Two configurations that look different are statistically tied

The report says so itself rather than letting the reader assume a ranking is meaningful:

> `paragraph+dense` leads `paragraph+bm25` by 0.017 recall, but the 95 % intervals overlap ([0.829, 0.975] vs [0.825, 0.950]). With 40 queries that is not enough evidence to call the top two apart — treat them as tied.

### 5. Embedding quality dominates everything else

Running the identical grid with the built-in hashing embedder — a character n-gram vectoriser with no semantic knowledge — inverts the leaderboard completely:

| configuration | nDCG (hashing) | nDCG (nomic-embed-text) |
|---|---|---|
| `paragraph+bm25` | **0.860** (1st) | 0.860 (6th) |
| `paragraph+dense` | 0.673 (9th) | **0.892** (2nd) |
| `paragraph+hybrid` | 0.769 (5th) | **0.895** (1st) |

BM25 scores identically in both columns — it never touches the embedder, which doubles as a sanity check on the harness. Everything dense moves by 15–22 points.

The practical reading: before tuning chunk sizes, check the embedding model. It is the larger lever by a wide margin.

## Quickstart

```bash
git clone https://github.com/Aphelion07/rag-eval-lab
cd rag-eval-lab
uv venv && uv pip install -e ".[dev]"
```

Runs with no model at all — the hashing embedder needs nothing:

```bash
rag-eval run --embedder hashing
```

With real embeddings:

```bash
ollama pull nomic-embed-text
rag-eval run --out docs/report.md --json docs/results.json
```

Diagnose a single query across all three retrievers:

```bash
rag-eval inspect --query q04
```

Sweep a different chunk size:

```bash
rag-eval run --chunk-size 256 --overlap 32 -k 10
```

## Design decisions

**BM25 is implemented rather than imported.** Its parameters are the point of the exercise: `k1` sets how fast repeated-term evidence saturates, `b` sets how hard long documents are penalised. Since chunking *is* length manipulation, `b` interacts directly with the variable being tested. A black-box dependency invites treating both as magic constants.

**Fusion uses ranks, not normalised scores.** BM25 scores are unbounded sums whose scale depends on corpus statistics; cosine similarities live in [-1, 1] and cluster near the top. Normalising makes them *look* comparable, but the transform depends on the score distribution of each individual query — so the same document wins or loses depending on what was retrieved alongside it. Rank is the only signal both express on the same scale.

**Metrics are scored per document, not per chunk.** Retrieving three chunks of the same file is one useful result. The retriever over-fetches 4× before deduplicating, so a fine-grained chunker cannot spend its whole budget on a single document.

**Chunk sizes are in characters, not tokens.** Token-accurate splitting would mean a tokenizer per model family. The comparison here is between splitting *strategies*, and a bias that applies equally to all of them does not change their ranking.

**Embeddings are cached to disk, keyed on model plus content hash.** A grid of 4 chunkers × 3 retrievers re-embeds the same corpus repeatedly; without the cache a sweep spends most of its wall clock recomputing vectors it already has.

**Queries are pre-embedded before timing begins.** They were not, at first — and the first dense configuration in the grid paid the embedding cost for all 40 queries while every later one read them from cache. It appeared as that one configuration being ~500× slower to query. The measurement was of cache state, not of retrieval.

## Testing

```bash
pytest -q --cov=rag_eval --cov-report=term-missing
ruff check . && ruff format --check . && mypy
```

**157 tests, 99 % coverage, mypy `strict`.** Nothing touches the network: the Ollama backend is covered by mocking at the HTTP layer with `respx`, and every other test runs against the in-process hashing embedder.

Metric expectations are worked out by hand in comments — a metric test that computes the expectation the same way the implementation does proves only that the code agrees with itself:

```python
def test_inverted_ordering_scores_below_one(self) -> None:
    # DCG  = 1/log2(2) + 2/log2(3) = 1.0 + 1.2619 = 2.2619
    # IDCG = 2/log2(2) + 1/log2(3) = 2.0 + 0.6309 = 2.6309
    # nDCG = 2.2619 / 2.6309 = 0.8598
    assert ndcg_at_k(["b", "a"], {"a": 2.0, "b": 1.0}, 2) == pytest.approx(0.8598, abs=1e-4)
```

The documented weaknesses are asserted rather than assumed, because the benchmark's premise depends on them — `test_is_blind_to_synonyms` proves BM25 really cannot match *"two-factor authentication"* to a document saying *"Enable 2FA"*, which is the entire reason the dense retriever exists.

## Limitations

- **The corpus is 24 documents.** Large enough for the retrieval strategies to separate, far too small to predict behaviour at 100k documents, where an approximate index becomes mandatory and its own recall enters the picture.
- **Relevance labels are single-annotator.** No inter-annotator agreement, so borderline grades reflect one person's judgement.
- **40 queries is a small sample.** This is why every mean carries a bootstrap interval and why the report refuses to declare overlapping configurations different.
- **Dense search is brute force.** Exact by design, so the benchmark measures the retriever rather than an index's approximation error — but it does not scale.
- **No reranking stage.** A cross-encoder reranker would likely shift the leaderboard and is the obvious next axis.
- **Generation is out of scope.** This measures retrieval only. Answer quality, faithfulness and citation accuracy are a separate problem.
