# rag-eval-lab

**A retrieval evaluation harness. It answers which RAG configuration actually finds the right documents, with confidence intervals, failure analysis, and no API key.**

## Why this is not another RAG chatbot

Most RAG projects demonstrate that a pipeline *runs*. Almost none demonstrate that it **works**, meaning the retriever actually puts the right document in front of the model instead of a plausible neighbour.

That gap matters because retrieval is the ceiling on everything downstream. A generator can't cite what retrieval never returned, and no amount of prompt engineering fixes a document that was never fetched.

So there's no chatbot in this project. Instead there's a corpus, a labelled question set, four chunking strategies, three retrieval strategies, and the machinery to say which combination actually wins and whether that win is real.

```bash
rag-eval run
```


## What it measures

| | |
|---|---|
| **Recall@k** | Did the relevant documents reach the top k at all? This is the ceiling on everything downstream. |
| **Precision@k** | How much of the top k is noise? Noise costs context window and dilutes attention. |
| **MRR** | How high did the first relevant document rank? |
| **nDCG@k** | Rank-weighted, and the only metric here that understands graded relevance, "answers it" versus "mentions it". |
| **hit rate** | Did the query get anything useful at all? The blunt question. |
| **Bootstrap CI** | A 95 % interval on every mean, so a two-point gap doesn't get mistaken for a real result. |
| **index / query time** | A configuration that wins on nDCG while querying six times slower hasn't obviously won. |

Reporting Recall@k alone is the easiest way to make a retriever look better than it is. This computes all of them, every run.

## The dataset

24 documents on IT security and networking, 40 questions, 66 graded relevance labels, written for this benchmark and generated by [`data/build_corpus.py`](data/build_corpus.py) so the design constraints stay visible and testable.

Adjacent topics get separate documents: symmetric vs asymmetric encryption, authentication vs authorization, TCP vs UDP, SQL vs command injection. A corpus of unrelated documents makes every retriever look good; the interesting failures only show up once the wrong answer is actually plausible.

Vocabulary is deliberately split, too. One document says "Enable 2FA", the query asking for it says "two-factor authentication". BM25 can't bridge that gap on its own (a test asserts it returns literally nothing), while other queries hunt exact strings like `port 22`, `A01`, `strcpy`, where the advantage flips the other way.

Relevance is graded, 2 for a document that answers the question and 1 for one that's merely related, so nDCG can tell a good ranking apart from a lucky one.

A test asserts that every document is reachable by some query, since an unlabelled document is dead weight: it can only hurt precision and never help recall.

## Findings

All figures from `nomic-embed-text` via Ollama, k=5, 40 queries. Reproduce with `rag-eval run`.

### 1. The trivial chunker wins

`paragraph`, one chunk per paragraph, no size budget, no overlap logic, took the top three places. The recursive splitter every RAG tutorial reaches for placed fifth, behind it on every single metric.

Not a universal law: this corpus has short, well-structured documents where paragraphs are already the natural retrieval unit, which is exactly the point. The sophisticated strategy isn't free, and here it buys nothing. A benchmark that skipped the trivial control would have quietly concluded the opposite.

### 2. BM25 never whiffs, it just ranks badly

Look at the hit column across all twelve configurations:

| retriever | hit rate | nDCG |
|---|---|---|
| BM25 (all four chunkers) | **1.000** | 0.841 – 0.860 |
| dense | 0.775 – 0.975 | 0.839 – 0.892 |
| hybrid | 0.925 – 0.975 | 0.870 – 0.895 |

BM25 found something relevant for every single query and still lost on ranking quality. Dense retrieval ranks better when it works and fails outright when it doesn't.

These are different risk profiles, not different amounts of quality. If a downstream generator can tolerate a mediocre ranking but not an empty context, hit rate is the metric to optimise for, and the "worse" retriever turns out to be the right call.

### 3. Hybrid retrieval can be worse than its own best component

Query q04, "How do I stop an attacker who guessed my credentials from getting in?":

```
$ rag-eval inspect --query q04
labelled relevant: ['authentication', 'two-factor-auth']

bm25                    dense                   hybrid (rrf)
  logging-monitoring      ssh                     logging-monitoring
  least-privilege      OK authentication          password-reset
  password-reset          csrf                    ssh
  buffer-overflow      OK two-factor-auth         least-privilege
OK authentication         password-reset          csrf
```

Both components retrieve something relevant on their own. The fusion of the two retrieves nothing.

Reciprocal Rank Fusion scores a document by summing `1/(k + rank)` across retrievers, which means it rewards agreement. Here both retrievers independently rank `password-reset` moderately well, and their agreement on that wrong answer outweighs `authentication`, which only one of them ranked highly. Fusion amplified the shared error and drowned out the one signal that actually mattered.

Every tutorial says hybrid retrieval beats either component alone. Usually it does. This is a reproducible case where it doesn't, and it's the reason the harness reports per-query failures instead of stopping at aggregates.

### 4. Two configurations that look different are statistically tied

The report says as much itself rather than letting the reader assume a ranking is meaningful:

> `paragraph+dense` leads `paragraph+bm25` by 0.017 recall, but the 95 % intervals overlap ([0.829, 0.975] vs [0.825, 0.950]). With 40 queries that is not enough evidence to call the top two apart, treat them as tied.

### 5. Embedding quality dominates everything else

Run the identical grid with the built-in hashing embedder (a character n-gram vectoriser with zero semantic knowledge) and the leaderboard flips completely:

| configuration | nDCG (hashing) | nDCG (nomic-embed-text) |
|---|---|---|
| `paragraph+bm25` | **0.860** (1st) | 0.860 (6th) |
| `paragraph+dense` | 0.673 (9th) | **0.892** (2nd) |
| `paragraph+hybrid` | 0.769 (5th) | **0.895** (1st) |

BM25 scores identically in both columns, since it never touches the embedder at all, which doubles nicely as a sanity check on the harness. Everything dense-based moves by 15 to 22 points.

The practical takeaway: check the embedding model before touching chunk sizes. It's the bigger lever, by a wide margin.

## Quickstart

```bash
git clone https://github.com/Aphelion07/rag-eval-lab
cd rag-eval-lab
uv venv && uv pip install -e ".[dev]"
```

Runs with no model at all, since the hashing embedder needs nothing:

```bash
rag-eval run --embedder hashing
```

With real embeddings:

```bash
ollama pull nomic-embed-text
rag-eval run --out docs/report.md --json docs/results.json
```

Diagnose a single query across all three retrievers:

```bash
rag-eval inspect --query q04
```

Sweep a different chunk size:

```bash
rag-eval run --chunk-size 256 --overlap 32 -k 10
```

## Design decisions

BM25 is implemented rather than imported. Its parameters are the whole point of the exercise: `k1` sets how fast repeated-term evidence saturates, `b` sets how hard long documents get penalised. Since chunking is itself a form of length manipulation, `b` interacts directly with the variable under test, and a black-box dependency would just invite treating both as magic constants.

Fusion works on ranks rather than normalised scores. BM25 scores are unbounded sums whose scale depends on corpus statistics, while cosine similarities live in [-1, 1] and cluster near the top. Normalising makes them look comparable, but the transform depends on the score distribution of each individual query, so the same document can win or lose depending on what else got retrieved alongside it. Rank is the one signal both sides actually express on the same scale.

Metrics are scored per document, not per chunk. Retrieving three chunks of the same file is one useful result, not three, so the retriever over-fetches 4x before deduplicating, which stops a fine-grained chunker from spending its entire budget on a single document.

Chunk sizes are measured in characters rather than tokens. Token-accurate splitting would mean shipping a tokenizer per model family, and since the comparison here is between splitting strategies, a bias that applies equally to all of them doesn't change their ranking anyway.

Embeddings get cached to disk, keyed on model plus content hash. A grid of 4 chunkers times 3 retrievers re-embeds the same corpus over and over, and without the cache a sweep would spend most of its wall clock recomputing vectors it already has.

Queries are pre-embedded before timing starts. They weren't, at first, and the first dense configuration in the grid ended up paying the embedding cost for all 40 queries while every configuration after it just read from cache. It looked like that one configuration was 500x slower to query. It wasn't. The measurement was of cache state, not of retrieval.

## Testing

```bash
pytest -q --cov=rag_eval --cov-report=term-missing
ruff check . && ruff format --check . && mypy
```

157 tests, 99 % coverage, mypy `strict`. Nothing touches the network: the Ollama backend gets mocked at the HTTP layer with `respx`, and everything else runs against the in-process hashing embedder.

Metric expectations are worked out by hand in comments, since a metric test that computes the expectation the same way the implementation does only proves the code agrees with itself:

```python
def test_inverted_ordering_scores_below_one(self) -> None:
    # DCG  = 1/log2(2) + 2/log2(3) = 1.0 + 1.2619 = 2.2619
    # IDCG = 2/log2(2) + 1/log2(3) = 2.0 + 0.6309 = 2.6309
    # nDCG = 2.2619 / 2.6309 = 0.8598
    assert ndcg_at_k(["b", "a"], {"a": 2.0, "b": 1.0}, 2) == pytest.approx(0.8598, abs=1e-4)
```

The documented weaknesses get asserted rather than assumed, because the benchmark's whole premise depends on them. `test_is_blind_to_synonyms` proves BM25 genuinely cannot match "two-factor authentication" to a document saying "Enable 2FA", which is the entire reason the dense retriever exists in the first place.

## Limitations

- **The corpus is 24 documents.** Large enough for the retrieval strategies to separate, far too small to say anything about behaviour at 100k documents, where an approximate index becomes mandatory and its own recall enters the picture.
- **Relevance labels are single-annotator.** No inter-annotator agreement, so borderline grades just reflect one person's judgement.
- **40 queries is a small sample.** That's why every mean carries a bootstrap interval, and why the report refuses to call overlapping configurations different.
- **Dense search is brute force.** Exact by design, so the benchmark measures the retriever itself rather than an index's approximation error, but it doesn't scale.
- **No reranking stage.** A cross-encoder reranker would likely shuffle the leaderboard and is the obvious next thing to add.
- **Generation is out of scope.** This measures retrieval only. Answer quality, faithfulness and citation accuracy are a separate problem entirely.
